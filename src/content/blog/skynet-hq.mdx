## One person, many projects, a phone

<Fig01Hero caption="A message from my phone goes to cos, cos passes it to a conductor, and the conductor starts the workers.">
  <ol>
    <li>I send a message from my phone through Claude Code Remote Control.</li>
    <li>cos, the Chief of Staff, receives the message and routes it.</li>
    <li>cos sends the work to the conductor of that project.</li>
    <li>The conductor starts short-lived workers, such as recon, architect, dev and verify.</li>
    <li>Each worker reports back to the session that started it.</li>
  </ol>
</Fig01Hero>

I work on several projects in my own time. I wanted to move them forward when I am away from my desk. In the design conversation, I put the goal this way: "I should be able to talk to my chief of staff from my mobile, from my laptop, anywhere."

Skynet HQ is the result. It is a crew of Claude Code sessions on my MacBook Pro, which I call Skynet. I talk to one session, the Chief of Staff, called cos, and to the conductor of a project when I need its details. cos starts one conductor for each project, and each conductor starts workers for single tasks.

Under the crew is a harness around Claude Code. Scripts start, relay and retire sessions. Hooks watch how much context each session uses. Files hold the contracts: timestamped prompts and reports, handoffs and ledgers. A linter checks the crew's own files.

This post shows how the crew is built and how work moves through it. Most of the post is about memory: how each session keeps its context sharp, and how the crew learns from its own records. {/* framing: the one-line outline of the post */}

Skynet HQ is private. I explain the design at a high level here. I do not publish the system.

## How the idea took shape with Claude

<Fig02bArc caption="Each idea from the design conversation, what the build made of it, and what the first day of use taught.">
  <ol>
    <li>Permissions. Designed: an allow list. Built: auto mode with deny rules, and the safety classifier as a second guard. Learned: the classifier blocked releases that came through another session, so conductors prepare, Dutt clicks.</li>
    <li>Relays. Designed: relay when context reaches a fixed share. Built: a percent or a token count, whichever comes first. Learned: the first dream found relays at about a fifth of the window, so the levels were raised per role.</li>
    <li>The dream. Designed: a nightly dream. Built: the crew's own dream worker and a scheduled job, because Claude Code has no documented dream feature. Learned: cos runs the dream at the end of the day.</li>
    <li>Viewing. Designed: terminal viewer windows. Built: Ghostty, plus a mode without tmux. Learned: four short commands, because tmux keys tripped me up on day 1.</li>
    <li>Worktrees. Designed: worktrees beside each repo. Built: one worktree root and no branch switching in my own checkout. Learned: worktrees are snapshotted and locked while in use.</li>
    <li>Reports. Designed: workers report to the conductor. Built: the same, plus a message log from a Claude Code mod. Learned: my words must be forwarded verbatim, because one decision was lost on day 1.</li>
  </ol>
</Fig02bArc>

I designed Skynet HQ with Claude in the Claude desktop app, on a Saturday evening in October 2026. The plan was to design for an hour and then build on the Mac.

Two problems started it. I used a large third-party skill pack, and I wanted a small set of skills made for my own work. I also coordinated agents by hand. I started an agent, and then I told another agent its name so that the two could exchange messages.

The design grew in steps. It began as one Chief of Staff with a few agents. Then it grew to one conductor per project, with workers under each conductor. Then I named the part that mattered most: "The most important aspect of the entire harness and orchestration process here is memory, context management."

The core ideas were inspired by the chief architect at my day job. His work showed me how to write handoffs with timestamps. It also showed me how to spawn agents, so that the work is spread out and each context is saved. He also gave me a pep talk on how memory works. It covered the four memory types, and what a dream cycle does and how to use it. I brought these ideas into the design conversation. Claude and I then built the crew around them, with the conductors, the handshake, the relays and the crew's own dream. I am grateful to him for his work and for his time. {/* framing: the last two sentences; Dutt to confirm the wording of the credit */}

Claude wrote a starter pack of docs, templates and scripts, and tested it in a sandbox. A Claude Code session on the Mac then built the real system from it in one night.

## The crew

<Fig02OrgChart caption="The crew has four levels at most, and a script checks who may start whom.">
  <ol>
    <li>Dutt: talks to cos, and to each conductor as needed, from a phone, a laptop or a browser.</li>
    <li>cos, the Chief of Staff: talks to Dutt, keeps the HQ ledgers, and starts and stops conductors. It never writes project code.</li>
    <li>Conductor, one per project: breaks features into tasks, starts workers, verifies, and merges task branches into the feature branch. It never writes implementation code.</li>
    <li>Workers: recon, research, architect, dev and verify. Each worker does one task and then retires.</li>
    <li>Helpers, such as an SME: answer one focused question for a worker. Helpers never start anyone.</li>
  </ol>
</Fig02OrgChart>

The crew is a tree, and I am at the top. I talk to cos most of the time. I also talk to each conductor directly when I need the fine details of its project or want to move it forward.

Each conductor owns one repository. A worker can start a helper to answer one question, so the worker does not spend its own context on it. In the design conversation, I said: "the idea is to save context."

One script starts every session. It checks that the parent may start that role. Messages between sessions are short nudges. Everything that matters goes into files.

Conductors send cos high-level updates only. A conductor alerts cos when it judges that something is important.

The harness can also hand work to a model from another vendor, through that model's own command-line tool. The first case was TinyTv, one of my apps. Its conductor had OpenAI's Codex draw 49 illustrations for the app, all from one style reference. It used my own sign-in, so there was no API spend, and I approved the drawings. The work used the usual files: a research task, ledger lines and dev tasks.

## How work flows

<Fig03Feature caption="One feature moves from my phone to cos, to a conductor and its workers, and back to me as a short status.">
  <ol>
    <li>I send an ask from my phone, such as: add X to project Y.</li>
    <li>cos records the ask in its inbox and writes a prompt file.</li>
    <li>cos sends the conductor a short message that points to the prompt file.</li>
    <li>The conductor runs recon, then an architect, who returns a task list with a file scope for each task.</li>
    <li>The conductor starts devs in parallel where their scopes do not overlap.</li>
    <li>Each dev reports with an exit code for every check.</li>
    <li>A verifier runs every claimed check again.</li>
    <li>The conductor merges the tasks that pass into the feature branch.</li>
    <li>The conductor sends cos a feature report.</li>
    <li>cos sends me ten lines or fewer: done, in progress, blocked, and what needs me.</li>
  </ol>
</Fig03Feature>

Devs run in parallel only when their tasks share no file. When the conductor is unsure, they run one after another.

<Fig04Handshake caption="A new worker proves that it is running with an ack before it gets the go.">
  <ol>
    <li>The parent writes a prompt file named with a UTC timestamp.</li>
    <li>The parent starts the worker in a named session.</li>
    <li>The worker reads only the goal of the prompt.</li>
    <li>The worker sends <code>ack: 20261025T065654Z ready</code>.</li>
    <li>The parent sends <code>go: 20261025T065654Z</code>.</li>
    <li>The worker does the work and writes its report.</li>
    <li>The worker sends <code>report ready: 20261025T065654Z status=done</code>.</li>
  </ol>
</Fig04Handshake>

The handshake came from my own flow in the design conversation.

<Fig05FilePair caption="Every task is two files with the same timestamp: the prompt and the report.">
  <ol>
    <li>The prompt file, written by the parent, has sections such as Goal, Scope and Acceptance check.</li>
    <li>The report file, written by the worker, has sections such as Summary and Evidence. The Evidence lists each check with its exit code.</li>
  </ol>
</Fig05FilePair>

If a report has no exit code for a check it claims, the task counts as blocked.

## Where things live

  <ol>
    <li><code>~/skynet-hq/bin</code>: the scripts that start, retire and relay sessions.</li>
    <li><code>docs</code>: the contracts, with the intent document first. <code>docs/templates</code> holds the file templates.</li>
    <li><code>ledgers</code>: the HQ ledgers for agents, asks, decisions and projects.</li>
    <li><code>knowledge</code>: cited facts for the whole crew.</li>
    <li><code>dreams</code>: one report for each dream.</li>
    <li><code>handoffs</code>: the handoffs of cos and of HQ workers.</li>
    <li><code>runs</code>: prompt and report pairs for HQ work.</li>
    <li><code>mods</code>: the Claude Code mod that draws the crew band.</li>
    <li><code>projects</code>: one registration file for each project.</li>
    <li>A repository's <code>.orchestration</code> folder: <code>runs</code>, <code>handoffs</code>, <code>knowledge</code>, <code>messages</code>, and the files <code>ledger.md</code>, <code>tasks.md</code>, <code>decisions.md</code> and <code>STATUS.md</code>.</li>
  </ol>
</Fig12Dirs>

Git ignores each repository's `.orchestration` folder through `.git/info/exclude`. So the crew's files never show in a diff or a pull request.

## Four kinds of memory

<Fig06Memories caption="Information moves from working memory into episodic, semantic and procedural memory, and then back into the next session.">
  <ol>
    <li>Working memory: one session's context window. It holds the prompt, the handoff and the files the session opened. It is scarce and short-lived.</li>
    <li>Episodic memory: what happened. Prompt and report pairs, handoffs, ledgers and the message log between agents.</li>
    <li>Semantic memory: what is true. Distilled facts, each with a source and a verified date.</li>
    <li>Procedural memory: how the crew works. Skills, agent definitions, contracts, docs and scripts.</li>
    <li>Reports, handoffs and ledgers move working memory into episodic memory.</li>
    <li>The dream turns episodes into cited facts in semantic memory.</li>
    <li>Proposals that are approved change procedural memory.</li>
    <li>A new session loads procedural memory, the knowledge index and the latest handoff.</li>
  </ol>
</Fig06Memories>

A long-running agent forgets things and repeats work. Skynet HQ treats each session's context window as scarce, short-lived working memory. Everything that matters lives outside it, in files. Claude said it in one line during the design: "A session is disposable; the files are the agent."

I learned the four memory types from the chief architect's talk. I brought them into the design conversation, where I said that episodic memory "will help us move the needle in terms of development." Semantic memory then improves the process itself.

Workers and conductors never edit procedural memory. Changes arrive as proposals, and each change that is applied is logged in the decisions ledger. cos may fix a small problem in the process directly, if no live agent breaks, and it logs that change too.

## Context: keep each session sharp, and the relay

<Fig07Context caption="As a session fills its context, it gets a checkpoint instruction, then relay instructions, and a fresh session takes over under the same name.">
  <ol>
    <li>The status line records how much context the session has used.</li>
    <li>A hook reads that number on every prompt and every tool call.</li>
    <li>Checkpoint level: write a checkpoint handoff now, then continue.</li>
    <li>Relay soon level: finish only the current step, then write a relay handoff.</li>
    <li>Relay now level: stop, write the relay handoff and request a relay. The instruction repeats until a new handoff exists.</li>
    <li>After compaction, an emergency instruction: rebuild a handoff from the files and relay.</li>
    <li>The parent reviews the handoff and adds notes. Generation 2 starts under the same name and reads the handoff.</li>
    <li>The levels differ by role. Workers relay first, conductors later, and cos last.</li>
    <li>On build day, the conductors relayed at about a fifth of the window.</li>
  </ol>
</Fig07Context>

Each session loads its contract first, then its prompt or its handoff. Then it loads a short knowledge index and only the files that these cite.

Before a session researches anything, it searches the knowledge files and earlier reports. If someone already found the answer, it cites that report. Long command output goes into a file, and the session searches the file.

Compaction is the failure case. Claude Code can compact a long session into a summary, but the model writes that summary under pressure, and it loses specifics. A relay keeps a handoff that the session writes on purpose, while it still has room to write it well.

A usage limit is not a reset. Once, requests failed until the wait passed, but the sessions and their context survived. A checkpoint before a known limit keeps the work safe.

The name stays the same, so messages and ledger lines still point to the right agent. On build day, a worker relayed in a test. Generation 2 finished the task and said that the handoff alone was enough.

A handoff passes one test. A fresh session that reads only the handoff and the files it cites can continue without a question to anyone. In the design conversation, I said handoffs exist "so that the future agents are not redoing the entire research or the same work again and again."

<Fig08ModBand caption="The crew mod draws a band above the prompt with the agent, its generation, its context bar and the live crew count.">
  <ol>
    <li>The agent's name and role.</li>
    <li>The relay generation, such as gen 2.</li>
    <li>A context bar in percent. The bar darkens as the level rises, and the label names the level.</li>
    <li>The next step, such as relay.</li>
    <li>The number of crew sessions that are live.</li>
  </ol>
</Fig08ModBand>

I watch the context from this band. The same mod logs every message between sessions to a file for each agent. That log becomes episodic memory, and no model spends effort to write it.

## Ledgers: the crew's diary

A ledger is append-only. Each event is one line, and the newest line is at the bottom. Nobody edits an old line, and a correction is a new line.

Each file has one writer. Two writers on one file is how a ledger gets corrupted. If a session needs a change in a file that it does not own, it sends a message to the owner.

| Ledger | What it records |
|---|---|
| Project ledger | Each worker's life: spawned, reported, verified, merged, retired |
| Agents | Every conductor and HQ worker that starts or retires |
| Inbox | Every ask from me, in my words, with its route and status |
| Decisions | Only what I decided, in my own words |
| Message logs | Every message a session sends or receives |

The decisions ledger keeps my exact words. The HQ rules say that nobody asks Dutt twice. A new session reads the decisions ledger before it asks me again. {/* framing: how 'nobody asks twice' works in practice */}

cos also keeps a private ideas store. It is my backlog of thoughts, and cos cleans it up each week.

Here are three lines from the contextsmith ledger on the first morning. I cut the details column short.

```text
| 20261025T065656Z | contextsmith-recon-diff-flow | spawned  | T-001 | parent cond-contextsmith |
| 20261025T065752Z | contextsmith-recon-diff-flow | retired  | T-001 | session closed |
| 20261025T065746Z | contextsmith-recon-diff-flow | reported | T-001 | done, citations spot-checked |
```

A recon worker started, reported and retired in about a minute. Now look at the times on the last two lines. The report happened first, but its line is below the retire line.

The conductor computed those timestamps by hand, so the ledger went out of order. The fix was one helper script that stamps the time at the moment of writing. All ledger lines now go through it. Episodic memory is useful only if the crew can trust it. {/* framing: the closing sentence of the paragraph */}

The first dream found a second problem. Seven rows were logged under the wrong agent, because a flag was in the wrong place. The helper now rejects that mistake.

## Lessons: catch surprises when they happen

When a session is surprised, it writes one line with a source. HQ lessons go into `lessons.md`, and each repository has a knowledge inbox.

These lessons are from the first two days. The Claude Code behaviour was observed on 2026-10-25 with Claude Code 2.1.310.

- Allow rules match the command as it was typed. So the crew calls its scripts by their full path.
- A decision that I made directly with a conductor never reached cos. So cos sent a later prompt that pointed to work I had rejected. Conductors now forward my exact words to cos in the same turn.

The last lesson became a rule on the same day.

A lesson is raw. The crew does not trust it yet. The dream decides which lessons become knowledge.

This post has a lesson of its own. A brief for it had nine wrong claims, and the architect found them when it checked the ledgers. The new lesson says that a brief for public writing must be checked against the ledgers first.

## Knowledge: what the crew knows to be true

Each fact is one line, with a source and the date when someone last verified it. This is a real line from the HQ index:

```text
- Call crew scripts by full path (`~/skynet-hq/bin/…`): allow rules match the command as typed. [src: lessons.md] (verified 2026-10-25)
```

That fact started as a lesson. The first dream moved it into the index.

When a newer episode contradicts a fact, the fact is corrected. The crew does not keep two versions of it.

HQ and each repository have a short `index.md` that every session loads at the start. Topic files load only when a task needs them.

An urgent fact goes in at once, if it would make the next worker fail. Everything else waits for the dream.

## The dream cycle

<Fig09Dream caption="The dream reads the day's episodes, writes cited facts, measures the crew and leaves proposals that wait for approval.">
  <ol>
    <li>Episodes come in: ledgers, reports, handoffs, lessons, each repository's inbox and the message logs since the last dream.</li>
    <li>The dream merges lessons into cited facts and corrects stale facts.</li>
    <li>It keeps each knowledge index under 150 lines and empties the lessons it used.</li>
    <li>It measures the memory system: relays per agent, context at relay, handoff failures, memory misses and verify failures.</li>
    <li>It writes proposals for changes to how the crew works. It applies none of them.</li>
    <li>A proposal waits for approval. An approved proposal becomes procedural memory.</li>
  </ol>
</Fig09Dream>

I learned about the dream cycle from the same talk. In the design conversation, I asked for "local dream cycles or else real Claude dream cycles." On build day, the build agent found no dream feature in the Claude Code 2.1.310 docs. So the crew runs its own dream.

A dream is one worker on Opus. cos starts it at the end of the day, or when I ask for one. A nightly job was built, but it is off, because overnight builds compete for usage.

The dream writes semantic memory directly.

The dream never edits code or deletes an episode. It also never changes how the crew works on its own. Procedural changes leave the dream as proposals. Each proposal is a concrete diff, with the episodes that justify it.

The proposals then need a decision. For the first dream, I gave the calls to cos: "As the chief of staff, I want you to make the decisions here." I added: "I don't want you to overkill the processes."

skynet-lint feeds the dream. It was the crew's first project: a small Rust tool that checks the crew's own files.

## The loop in its first days

<Fig06xLoop caption="By day the sessions write episodes and lessons, and at night the dream turns them into facts and proposals for the next morning.">
  <ol>
    <li>Day: each session writes reports, handoffs, ledger lines and messages into episodic memory.</li>
    <li>Day: a surprise becomes one cited line in the lessons file or a repository inbox.</li>
    <li>Day: a full session writes a handoff, and its next generation continues under the same name.</li>
    <li>Night: the dream reads the episodes and the lessons.</li>
    <li>Night: cited facts go into knowledge, and metrics and proposals go into the dream report.</li>
    <li>An approved proposal changes procedural memory: skills, contracts and docs.</li>
    <li>The next morning, sessions load the new procedural memory and the knowledge index at start.</li>
  </ol>
</Fig06xLoop>

The first dream ran on 25 October 2026, a few hours after the crew did its first real work. It read the files of HQ and of each project that had run work.

It found that the conductors doing real work relayed at about a fifth of their window. That was where the token level fired, and it was too early for a conductor. One conductor went from generation 1 to generation 6 in about 1 hour 40 minutes. Another went through three relays in about 70 minutes.

Three handoffs failed the test. One successor rebuilt its task board from git. Another needed a name clash explained. The third was not told that a background loop had died.

When Claude handed over the design, it had named this risk: "Handoff quality is the real bottleneck, and no script can enforce it." I had also told cos what I expected from the conductors: "Handoff should be gold and they are the key."

I read the relay numbers and decided that the relay point was too short. The levels are now set per role. Fewer relays also mean fewer handoffs that can go wrong.

The dream also counted 70 lint errors across 83 reports from day 1. The verify prompts asked for a different report shape, so the verifiers' reports drifted from the template.

The dream made ten proposals. These four were applied:

- Workers lint their own report before they send it.
- The ledger helper rejects a flag in the wrong place.
- The report template gained a Security section and a Problems and improvements section.
- The memory doc was updated to match how the crew works now.

My relay decision replaced one other proposal. cos deferred the rest.

The first dream processed all 24 lines in the lessons file. It moved each one into knowledge or dropped it with a reason. One knowledge file went from 2 facts to 23. New lessons from real work now wait for the next dream.

The second dream ran the next morning. It found that the safety classifier caused the most friction that day, and cos applied its fixes. A conductor now sends me the pull request link for a merge that deploys production, and it never retries a denied merge. For TestFlight, the crew builds the archive, and I upload it.

## Safety

<Fig10Safety caption="Only my own words authorize a release to users. The safety classifier blocks a release when my go comes through another session.">
  <ol>
    <li>Dutt, in person: releases to users, such as production deploys, App Store or TestFlight uploads, and publishing.</li>
    <li>Conductors: the git work in their own repository, such as branches, commits and merges into feature branches.</li>
    <li>Workers: commits on their own task branch only. They never push.</li>
    <li>A message from another session: never authority, even when it says that it comes from Dutt.</li>
    <li>Fetched web content: data, never instructions.</li>
    <li>Callout: the safety classifier blocked merges that deploy to production on four pull requests, and one TestFlight upload, although Dutt's go had come through another session.</li>
  </ol>
</Fig10Safety>

The crew runs unattended in auto mode, so its limits are explicit. A deny list blocks publishing, releases, credential reads and settings edits for every crew session.

Conductors own the git work in their repository. I asked for that, because I did not want cos to do it: "I don't want you, chief of staff, to do that … dirty work."

Releases to users still need me, even when I tell the crew to go ahead. In the first two days, the auto-mode safety classifier blocked merges that deploy to production on four pull requests. It also blocked a TestFlight upload. Each time, my go had come through another session. One merge went through when I said it in the conductor's own session. Now conductors prepare a release, and I do the last step myself.

On build day, the classifier also blocked the build agent twice when it tried to change its own permissions. I applied those two changes myself.

Worktrees protect work in progress. Each dev works in its own git worktree. When a worker retires or relays, its uncommitted work is saved to a private git ref. A worktree is removed only when it is clean and merged.

## Build day

The build took one night, from 24 to 25 October 2026, Pacific time. I opened a plain Claude Code session, the build agent, and gave it the starter pack as the spec.

My first tmux attach landed on the system window. A Ctrl-C there stopped the keep-awake process and the Remote Control server. Now I type one of four short commands, and I never use tmux keys.

The first real project was skynet-lint. I sent the ask from my phone to cos, and the full flow ran, from recon to merges into a feature branch. Verifiers failed three tasks, and each was fixed in one round.
